# Security

## Reporting a problem

Do not open a public issue. Email the project owner directly with what you found and how to reproduce it.

## What is in place now (chunks C00 to C18)

| Area | Control | Proven by |
| --- | --- | --- |
| Secrets | Read from environment only; app refuses to start with a short or repetitive key, wildcard origins or hosts, a non-MySQL URL, or (in production) non-HTTPS origins. `.env` is git-ignored; CI scans every push for committed secrets. | `api/tests/test_config.py`, gitleaks job |
| Logs | Every log line, including stack traces and library logs, passes through a redactor for PAN, GSTIN, email, long numbers and tokens. Request logs never include the query string. | `api/tests/test_logging.py`, `test_security.py` |
| Responses | Security headers on every response including errors; no server banner; API docs off in production; generic 500s with a request id; validation errors never echo submitted values. | `api/tests/test_security.py` |
| Requests | Host allow-list, exact-origin CORS, request-size limit (also for chunked bodies), request-id sanitising. | `api/tests/test_security.py` |
| Database | MySQL strict mode, UTC session, UTC-only timestamps (naive values refused), utf8mb4. | `api/tests/test_migrations.py` |
| Web app | Strict CSP (scripts from our own files only), no raw-HTML injection allowed by lint, no tokens in browser storage, service worker never touches `/api` or non-GET requests. | `web` lint, build, `deploy/nginx` |
| Dependencies | Exact pins, `pip-audit` and `npm audit` fail the build on known vulnerabilities; weekly Dependabot. | CI |
| Network | Dev services listen on 127.0.0.1 only. | `scripts/dev-up` |
| Passwords | Argon2id; at least 12 characters, no composition rules, common and personal passwords refused; the same effort is spent on unknown accounts so they are not faster to reject. | `api/tests/test_passwords.py`, `test_login.py` |
| Guessing | Account locks for 15 minutes after 5 wrong passwords; one address is limited to 20 failures per 15 minutes; every failure looks the same to the caller. | `api/tests/test_login.py` |
| Sessions | Random cookie, only its hash is stored; HttpOnly, SameSite=Lax, `__Host-` prefix and Secure in production; 12-hour limit; ended on sign-out, disable, password reset and password change. | `api/tests/test_login.py`, `test_sessions.py` |
| Forged requests | CSRF token on every state-changing request, plus a check that the `Origin` is ours (also on sign-in). | `api/tests/test_login.py`, `test_security.py` |
| Access control | Every route needs a role; a test fails if any route is open by accident. Administrator-only routes are tested against every role. Roles are read from the database on each request, so changes apply at once. | `api/tests/test_authz.py`, `test_admin_users.py` |
| Two-step sign-in | Staff and Administrators need a code from an authenticator app. A correct password earns only a single-use challenge (5 minutes, 5 attempts); the session cookie is issued only after the code is verified, and a test proves sessions are created in exactly one place. Codes cannot be replayed; wrong codes count towards the account lockout; recovery codes (10, single use, stored as keyed hashes) cover a lost phone; the authenticator secret is stored encrypted. | `api/tests/test_totp.py` (RFC 6238 vectors), `test_mfa_flow.py` |
| Inactivity | Staff and Administrator sessions end after 20 minutes without activity, measured on every request; the screen also signs out by itself so a forgotten tab does not keep showing data. | `api/tests/test_idle.py`, `web` tests |
| Every endpoint, every caller | Each endpoint is called as Administrator, Staff, Consultant, a signed-out visitor, someone with a temporary password, and four kinds of dead session (disabled, revoked, idle, expired), against a table written by hand from the BRD. Forged-request and foreign-origin checks run on every state-changing route. Breaking the code on purpose makes these tests fail (checked). | `api/tests/test_authz_matrix.py`, `brd_matrix.py` |
| Audit trail | Sign-ins (each step), failures, lockouts, sign-outs, refused requests (wrong role, missing CSRF token, foreign origin, dead session) and every account change are recorded with who, when, from where and the request id. Entries for a change are saved in the same transaction as the change, so neither exists without the other; failures and refusals are saved in a transaction of their own so they survive the request failing. Each entry is numbered with no gaps and carries a SHA-256 hash over its contents and the previous entry's hash. MySQL triggers refuse any UPDATE or DELETE of an entry, and any insert that skips a number or forks the chain; the app's database account cannot truncate the table, alter it or drop the triggers. Details are redacted like the logs. | `api/tests/test_audit.py` |
| Tamper detection | The whole trail is re-checked daily (systemd timer in `deploy/systemd/`), on request, and with every export: numbering, links and every hash, read in one consistent snapshot. Each passing check records the newest entry's hash, and the next check confirms it is unchanged, so even a rewrite that recomputes every hash is caught (unless the check history is rewritten too). Check results are append-only. A failure is logged at CRITICAL, written to the trail, and shown to every Administrator on every screen until a later check passes. The newest verified hash is also written to the application log, which gives an anchor outside the database once logs are shipped off the server. | `api/tests/test_audit_verify.py` (each kind of tampering), `test_admin_audit.py` |
| Audit viewer and export | Administrator only: filter by event, person, record and India dates; export to CSV headed by a fresh chain check, with the hashes so auditors can verify independently. Spreadsheet formulas in cells are neutralised. Every export is itself recorded. Nothing offers to edit or delete an entry. | `api/tests/test_admin_audit.py`, `web` tests |
| Packages and calendars | Administrator only. Published versions of packages and calendars, and the filings and checklist items under them, cannot be changed or deleted: database triggers refuse it, so cycles can always show exactly what they were built from (FR-PK-05). Every change is audited. Money is stored in whole paise, never as floating point. | `api/tests/test_catalog.py` |
| Clients | Opening a client is checked on the server for every request: the Administrator sees all, Staff only clients they own (a test proves another Staff member is refused). Staff can only create clients they own. Client IDs come from a database counter, can never be changed or reused, and clients cannot be deleted. PAN and GSTIN are validated (GSTIN by its check character) and unique; a duplicate names the existing client, but not its name when the person asking cannot open it. PAN, GSTIN, email and phone never go into audit details. PAN is masked on screen until "Show" is pressed. Consent changes are kept in an append-only log. Search only ever returns a Staff member's own clients, even when asked by another owner's ID or a known PAN; PANs are masked in lists. Changing owner, package or status needs a reason and goes into an append-only history; a reassigned client is closed to its previous owner from their very next request; only the Administrator reopens a closed client. | `api/tests/test_clients.py`, `test_clients_maintain.py` |
| Cycle stages | The server holds the only list of allowed stage moves and refuses anything else, including any skip; a move names the stage it expects, so a double click or two people at once cannot move a cycle twice. Returning work needs a note. Ticket numbers come from a counter and cannot be changed or reused; stage history and state events are append-only. Only the client's owner and the Administrator see or move a ticket; a task's assignee also sees that one task (not the client or its other tickets) and can only change its status, and loses it on the next request if reassigned. Not yet enforced: assignment details (C21), maker-checker on approve (C22), filing proof on "Mark filed" (C23). | `api/tests/test_tickets.py` |
| Due-date extensions | Only the Administrator can apply one, and only with a reason; it moves open cycles only (filed and closed ones keep their dates), and only to a later date. Applying names how many cycles the preview showed and changes nothing if that has changed since. The filing row is locked while it applies, and the cycle generator waits on it, so a cycle made at the same moment cannot miss the new date. Each extension, and each cycle's old and new dates, are append-only, and one audit entry records the whole change. | `api/tests/test_extensions.py` |
| Email | Nothing is emailed from a request: emails go into an outbox and a separate worker sends them, so a slow or failing mail server never holds up the app or loses an email. Templates are fixed text with named blanks (no template language, so nothing in a value runs); every blank must be filled; the subject is kept to one line and the header API refuses line breaks, so values cannot add headers or recipients. Addresses are validated. Once queued, an email's recipients and text cannot be changed, its status only moves forward, emails are never deleted and each step is kept (database triggers). Production requires STARTTLS or TLS to the mail server (unless it is a relay on the same machine) with certificate checks. Delivery reports must carry an HMAC-SHA256 signature over a timestamp and the body (compared in constant time; more than 5 minutes off is refused, so a captured report cannot be replayed later; a repeat inside that window changes nothing); without a configured secret the endpoint does not exist. Addresses never go into logs or audit details. The outbox is visible to the Administrator only. A failed audit log check emails every Administrator, at most once a day. | `api/tests/test_email.py` |
| Client links | A client reaches the portal only through a private link for one client and one cycle: 256 random bits, stored only as a SHA-256 hash, carried in the URL fragment (never sent to a server, so not in server or proxy logs or Referer headers) and removed from the address bar once read. A link opens once (a row lock stops two clicks both opening it) and starts a portal session with its own HttpOnly, SameSite=Strict cookie (`__Host-` in production), also kept only as a hash, lasting until the link's expiry (72 hours by default). Signing out needs a CSRF token derived from the session. A new link stops earlier unopened ones; a withdrawn link, a closed client or a closed cycle ends the portal at once. A reused, expired or replaced link explains itself and offers a new link, which is emailed to the client's primary contact on file (never shown), once per old link and at most 3 times a day per cycle. Refusals for known links are audited; unknown tokens are only logged, so guessing cannot fill the audit log. Links and their use cannot be rewritten or deleted (triggers). Only the client's owner and the Administrator make or withdraw links; a link to copy is shown once. | `api/tests/test_portal.py` |
| Client updates | No client update leaves the system without a person pressing Send (CR-03). Each state change (cycle stage, task status, client status) makes exactly one draft in the same transaction: drafts are tied one-to-one to state events by a unique key, and an event can be marked handled only once (trigger), so a race cannot draft twice; the send worker sweeps up any change that missed its draft but never sends one. Send locks the email row and requires it to still be a draft, so a double click (or two people) queues it once; the text is then frozen. It goes to the current primary contact, plus only contacts of the same client the sender ticks. Only the client's owner and the Administrator see, preview or send updates. Every send is audited (who, which email, how many copied; no addresses). Locking reads now always refresh the record from the database, so a value read earlier in the same request cannot defeat a lock (this fixed a double send found by the concurrency test). | `api/tests/test_client_updates.py` |
| Documents | Files are encrypted before they are stored: each with its own random AES-256-GCM key, itself sealed with a master key (`LL_STORAGE_KEY`, required in production) kept apart from the database; both seals name the file's random storage name, so one file cannot be passed off as another, and tampering is detected on read. Stored files are never overwritten (a second write to the same name fails) and are written readable only by the service account. A file's type is checked from its content, not its name (a renamed executable is refused); macro-enabled Office files are refused; names are cleaned of folders and control characters. Every file is scanned by ClamAV before it is stored: an infected file is never stored, is refused with a reason, and is logged and audited. If the scanner is down, the file is stored but shown to no one until a later scan (every 5 minutes) clears it; one found infected then is destroyed and its record kept. A new upload is a new version; versions and their scan results cannot be rewritten or deleted (triggers). Uploads are raw request bodies (no multipart parser) on a separate path with its own size limit (20 MB). There is no public file address: a download is a 5-minute link signed for one person, checked again against their session and their access to the client when used, and served as an attachment with `nosniff`, `no-store` and a sandboxing CSP. Every link made and every download is audited. Only the client's owner and the Administrator can see, upload or download a cycle's documents. | `api/tests/test_documents.py` |
| Client uploads | A client uploads only through a live portal session (C14), only against the checklist items of that session's one cycle (an item of any other cycle is "not found"), and only with the session's CSRF token. Every upload passes the same type, size and virus checks as staff uploads; a refused file comes back with its reason in words for the client and is recorded in the audit log (who, which item, why; no file content). Clients see only the names of their own files and whether they have been checked; they cannot download anything. Each cycle's checklist is a frozen copy taken from its package version when the cycle is made, and cannot be changed or deleted (triggers). | `api/tests/test_checklist.py` |
| Client alerts | Automatic alerts and reminders go only to the client's primary contact on file, only for active clients whose cycle is still collecting documents and still lacks a required document, and only within the configured India-time hours. Each carries a new private link (replacing earlier unopened ones). At most one alert per cycle per day is enforced by a unique key, one run at a time by a database lock, and each cycle is handled under a row lock in its own transaction; alert records cannot be changed or deleted. Every alert is audited. Client emails that fail, bounce or are still being retried are flagged on the owner's work list at once and stay there until someone marks them followed up (audited). | `api/tests/test_alerts.py` |
| Cycle generator | Makes only missing cycles; the database refuses a second cycle for the same client, filing and period; one run at a time (a database lock); each client in its own transaction. Closed clients get none. Every run is recorded; a failure is logged at CRITICAL, written to the audit log, and shown to every Administrator with a "Run again" button until a run succeeds. Errors record client IDs and error types only, never personal data. | `api/tests/test_generator.py` |
| People | Administrator creates and disables accounts; disabling takes effect on the very next request; the last Administrator cannot be locked out; consultants need a recorded agreement date (enforced by the database too). | `api/tests/test_admin_users.py` |

## Not built yet (and where it comes)

A failed audit check is emailed only if email is working; make sure CRITICAL log lines also reach someone (C31). Records of client data being viewed and downloaded arrive with that data (C07 onwards, C16). Also to come: consultant sign-in by emailed link and code (C21, so consultants cannot sign in yet); owner and assignment checks on real records (C07, C21; the matrix in `brd_matrix.py` lists the other 15 BRD capabilities and the chunk that builds each); PAN and bank masking, encryption review and independent security test (C30).

Known limits of the audit trail today: the hashes are plain SHA-256, so someone holding the database owner's account could drop the triggers, rewrite the trail and recompute every hash; the daily check catches that unless the check history is rewritten too, and shipping the logged hashes off the server (C31) or keeping exported copies elsewhere closes that gap. If the database is unreachable when a refusal or failed sign-in is being recorded, the request is still refused and the missing entry is logged as an error (`audit entry not written`) rather than turned into a server error. Entries for changes never go missing this way: if they cannot be written, the change is not saved either.

Known limits of two-step sign-in today: whoever uses a new account's temporary password first sets up its authenticator, so hand the password over directly and check the Team screen shows "Two-step on" afterwards. The authenticator secret is encrypted with a key derived from `LL_SECRET_KEY`: changing that key makes existing authenticators unreadable, and an Administrator would need to reset them. If the only Administrator loses their phone and recovery codes, `python -m app.cli reset-mfa --email ...` (needs server access) clears it.

## Production checklist (before any real data)

- TLS in front, using `deploy/nginx/`; set `LL_ENV=production`, exact `LL_ALLOWED_HOSTS` and https `LL_ALLOWED_ORIGINS`.
- Run uvicorn with `--no-server-header --proxy-headers --forwarded-allow-ips 127.0.0.1`, bound to 127.0.0.1 behind the proxy, so the address limit sees real client addresses.
- Create the first Administrator with `scripts/create-admin`; there is no web sign-up.
- Separate database accounts: `LL_MIGRATION_DATABASE_URL` (owner: all rights on the database, runs `alembic upgrade head`) and `LL_DATABASE_URL` (app: `SELECT, INSERT, UPDATE, DELETE` only). The app refuses to start in production without both, or with both naming the same account. Creating the audit triggers needs `SUPER` or `log_bin_trust_function_creators = ON` while binary logging is on.
- Install and enable `deploy/systemd/ledgerline-audit-check.timer` (daily audit log check) and `ledgerline-cycles.timer` (daily cycle generator), and confirm `systemctl list-timers` shows both.
- Hosting in India as required by the BRD (open question Q6).
