# Ledgerline - Change Requests to BRD v1.0

The BRD (section 16) says anything not written there needs a change request. These three came from the project owner on 8 Oct 2026. Status: **Proposed**, pending Administrator approval. CR-03 touches how alerts behave, so Partners should also see it.

## CR-01 Client ID

| Item | Detail |
| --- | --- |
| Requirement | Every client is assigned a 6-digit client ID when the record is saved. |
| Affects | FR-CL-01, FR-CL-06, section 10 (Client data) |
| Rules | Numeric, exactly 6 digits, from 100001 upward. Generated by the system from a database counter, never typed by a user. Unique. Cannot be changed. Never reused, including for closed clients. Searchable. Shown on client screens, emails and exports. |
| Acceptance | Saving a client returns a 6-digit ID. Two clients never share an ID. An attempt to edit the ID is refused. Search by ID finds the client (staff see only their own). |
| Note | The client ID is a reference, not a secret. Access is always checked on the server (NFR-SE-01), so a guessed ID gives nothing. |
| Built in | C07, C08 |

## CR-02 Every task is a ticket

| Item | Detail |
| --- | --- |
| Requirement | Every task is a ticket and has an ID. |
| Affects | Section 10 (Cycle data), FR-CY-01, FR-CY-02, FR-IN-04, FR-RP-01 |
| Rules | ID format `TKT-000001`, from a database counter, unique, never reused. Every filing cycle gets a ticket automatically when it is created (type FILING). Staff can also create ad hoc tickets (type TASK) for work that is not a filing. A FILING ticket's stage is the cycle stage in FR-CY-02. Tickets belong to one client. |
| Acceptance | A new monthly client shows 12 cycles, each with its own ticket ID. Creating an ad hoc task returns a ticket ID. Search by ticket ID works. |
| Built in | C09, C10, C11 |

## CR-03 Client email on every state change, sent manually

| Item | Detail |
| --- | --- |
| Requirement | The client gets an email at every state change, but it is sent manually when staff click a button. |
| Affects | Section 6 (process), FR-AL-06, FR-WF-06 |
| Rules | A state change is (a) any cycle or ticket stage change and (b) any client status change (active, paused, closed). Each state change automatically creates one **draft** email. The system never sends a draft by itself. On the ticket page, staff with access to that client see the draft, can preview it and add a note, and click **Send update to client**. The email goes to the client's primary contact; other contacts are copied only if the sender chooses. A draft can be sent once. Sending is audited and shows delivery status (queued, sent, delivered, failed, bounced). |
| Unchanged | Scheduled alerts and reminders (FR-AL-01, FR-AL-03) stay automatic. They are not state changes. |
| Acceptance | Moving a ticket through every stage produces one draft per move and no email until a click. Double-clicking Send sends one email. A user without access to the client cannot send. Every send has an audit entry. |
| Built in | C13, C15, C23 (test), C35 (completion email is also manual) |

## Assumptions to confirm

1. "State change" means cycle or ticket stage changes plus client status changes. If you meant only stage changes, ticket LL-065 ("Client status changes also create drafts", in C15) is dropped.
2. Scheduled pre-due-date alerts and reminders stay automatic. If you want those manual as well, FR-AL-01 and FR-AL-03 must change, and BO-1 (no late filings from internal tracking failure) is at greater risk.
3. Sequential client IDs are acceptable. If you prefer random, non-guessable 6-digit numbers, C07 changes to generate and check for collisions, with only about 900,000 possible values.
